# 대출 오퍼 타겟팅 분석 — 성사율과 효율의 불일치

**성사율이 높은 신청과 실제로 이익이 되는 신청은 같은가.** 네덜란드 금융기관의 대출 신청 처리 로그(BPI Challenge 2017, 신청 31,509건·이벤트 120만 건)를 분석해 이 질문에 답했다. 답은 "같지 않다"이며, 그 차이를 자원 배분 규칙과 시스템 요구사항으로 옮기는 데까지 진행했다.

## 핵심 결론

세그먼트를 접수 시점에 알 수 있는 정보만으로 39개로 나눠 보면 **성사율 순위와 공수 대비 효율 순위의 상관은 0.669**이고 부트스트랩 90% 구간 0.610~0.692도 모두 판정 경계 0.7 아래에 있다. 같은 공수를 효율 순서로 배분하면 공수 예산 50% 지점에서 **확보되는 대출 규모가 13.2% 많다**.

성사율이 높은 쪽은 소액·중액 신청이다. 효율이 높은 신청은 대형 신규 신청인데 성사율로는 낮은 축에 든다. 성사율은 대출 규모와 약하게만 같이 움직이기 때문에(순위 상관 0.454) 성사율만 보면 규모의 차이를 놓친다.

![성사율이 높은 세그먼트와 효율이 높은 세그먼트는 일치하지 않는다](outputs/charts/p5_rate_vs_eta.png)

## 지표

효율 η = R̄ × p / Ē 로 정의한다. R̄는 성사 신청이 수락한 오퍼 금액의 평균, p는 성사율, Ē는 세그먼트 모든 신청의 평균 공수다. 마진율과 공수 단가는 알 수 없으므로 두 미지수를 비율 하나로 접었다. 기대값이 음수가 되는 조건은 "공수 단가 ÷ 마진율 > η"이며, 세그먼트 순위는 두 미지수와 무관하게 정해진다.

공수는 업무 항목의 작업 구간을 합해서 잡았다. 대기 시간은 넣지 않았고, 방치 구간은 활동별 p99로 잘랐다. 모집단 전체 공수는 17,957.7시간이다.

## 권고

권고는 전제와 함께 쓴다.

1. **접수 시점 세그먼트에 따른 처리 우선순위 조정 — 조건부 1순위.** 인력이 실제 제약이라면 효율 순서로 대기열 순서를 정한다. 인력에 여유가 있다면 순서 변경은 대기 시간을 재배분할 뿐이므로 13.2%를 기대하지 않는다.
2. **첫 상담 단일 오퍼는 시범 후 판단한다.** 의사결정 지점이 월 309건뿐이라 A/B 검증에 8.4~63.4개월이 걸리므로 되돌릴 수 있는 시범 규칙과 전후 비교로 대체한다.
3. **오퍼 발송 후 접촉 정책 — 입력란 확보 후 A/B.** 자동 취소율을 2%p 낮추는 효과라면 5.5개월이면 판별된다. 다만 접촉 결과 코드가 기록되지 않으면 무엇이 달라졌는지 잴 수 없다.
4. **처리 속도 개선 단독으로는 권고하지 않는다.** 모든 세그먼트에서 고객이 시간의 과반을 쥐고 있다.

요구사항은 제품 이름 없이 26개(기능 7·데이터 8·측정 5·비기능 6)로 정리했고, 실현 경로는 세 가지로 비교했다. 규정·운영 변경만으로는 Must 요구사항 17개 중 11개를 충족하고 6개가 부분에 그친다. 코어 주변에 도구를 붙이면 17개를 모두 충족한다. 입력 항목까지 해결하려면 코어를 바꿔야 하는데 되돌리기 비용이 크다. 상세는 [`docs/09_requirements.md`](docs/09_requirements.md)와 [`docs/10_options.md`](docs/10_options.md)에 있다.

## 한계

- 관측 데이터의 연관이지 개입 효과가 아니다. 배분 비교는 관측된 세그먼트 평균으로 계산한 가상 배분이다.
- 복수 오퍼의 우위에는 선택 편향이 섞여 있다. 나중 상담은 고객이 남아 있어야 생기므로 상한으로 읽어야 한다.
- 실행 이후 성과(연체·부도·조기상환)와 조달비용 자료가 없어 손익 부호를 직접 판정하지 못한다.
- 단일 기관·단일 연도의 로그를 썼다.

## 재현

Python 3.12를 기준으로 한다.

```
py -3.12 -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python analysis/00_build_cache.py
.venv\Scripts\python -m pytest tests -q
```

원본 로그는 저장소에 포함하지 않는다. BPI Challenge 2017 데이터를 4TU.ResearchData에서 내려받아 `analysis/config.py`의 경로를 맞춘 뒤 `00_build_cache.py`로 parquet 캐시를 만든다. 이후 스크립트는 번호 순서대로 실행한다. 판정 로직은 모듈에 두고 합성 데이터로 검증하며, 테스트는 63개다.
